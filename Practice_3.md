## 1. Архитектура MVVM

MVVM разделяет ответственность за отображение, состояние интерфейса и работу с данными. `Activity` отвечает за элементы интерфейса и передачу действий пользователя. `ViewModel` вызывает UseCase и публикует состояние через `LiveData`. UseCase используют репозитории, а конкретные реализации репозиториев работают с источниками данных.

`ViewModel` не должна хранить ссылки на `Activity`, `View` или Activity-контекст. Зависимости передаются ей через конструктор; для их создания используется фабрика. При обычном изменении конфигурации, например повороте устройства, `ViewModelProvider` возвращает существующий экземпляр ViewModel для той же области жизненного цикла.

## 2. MovieProject: ViewModel и LiveData

### 2.1. Создание MainViewModel

В пакете `ru.mirea.khrechko.movieproject.presentation` создан класс `MainViewModel`, наследующий `ViewModel`. Он получает `MovieRepository` через конструктор и создаёт необходимые UseCase:

- `SaveFilmToFavoriteUseCase` — сохранение любимого фильма;
- `GetFavoriteFilmUseCase` — получение сохранённого фильма.

Результат операций хранится в `MutableLiveData<String> favoriteMovie`. Наружу он предоставляется через `LiveData<String>`, чтобы Activity могла наблюдать за значением, но не изменять его напрямую.

Ключевые методы ViewModel:

```java
public LiveData<String> getFavoriteMovie() {
    return favoriteMovie;
}

public void saveMovie(String name) {
    Movie movie = new Movie(2, name == null ? "" : name.trim());
    boolean saved = saveFilmUseCase.execute(movie);
    favoriteMovie.setValue(saved
            ? "Фильм сохранён"
            : "Не удалось сохранить фильм. Введите название.");
}

public void loadFavoriteMovie() {
    Movie movie = getFavoriteFilmUseCase.execute();
    if (movie == null) {
        favoriteMovie.setValue("Любимый фильм не найден");
    } else {
        favoriteMovie.setValue("Любимый фильм: " + movie.getName());
    }
}
```

В конструкторе и методе `onCleared()` добавлено логирование, позволяющее наблюдать за жизненным циклом ViewModel в Logcat.

### 2.2. Фабрика ViewModel

Класс `ViewModelFactory` реализует `ViewModelProvider.Factory`. Фабрика получает `Context`, сохраняет ссылку на `applicationContext`, создаёт `SharedPrefMovieStorage`, `MovieRepositoryImpl` и передаёт репозиторий в `MainViewModel`. Таким образом, создание объектов хранения и репозитория не выполняется внутри Activity или ViewModel.

```java
viewModel = new ViewModelProvider(
        this, new ViewModelFactory(this)
).get(MainViewModel.class);
```

### 2.3. Изменения в MainActivity

`MainActivity` получает поля ввода и элементы интерфейса, создаёт ViewModel через `ViewModelProvider` и подписывается на `favoriteMovie`:

```java
viewModel.getFavoriteMovie().observe(this, textView::setText);
```

Обработчики кнопок только передают действия во ViewModel:

```java
findViewById(R.id.buttonSave).setOnClickListener(v ->
        viewModel.saveMovie(text.getText().toString()));
findViewById(R.id.button).setOnClickListener(v ->
        viewModel.loadFavoriteMovie());
```

В результате Activity не вызывает UseCase и не содержит бизнес-логику сохранения или загрузки фильма. Внешний вид экрана с полем ввода, кнопками и текстом результата оставлен без изменений.

## 3. FoodScan: ViewModel на экранах

В проекте `FoodScan` добавлены ViewModel для авторизации, главного экрана и страницы продукта, а также фабрика для их создания. Используется существующий `ServiceLocator`, поэтому исходное разделение проекта на пакеты и папки сохранено. Интерфейс оставлен простым: используются существующие поля, кнопки, текстовые сообщения и стандартные диалоги.

### 3.1. AuthViewModel

`AuthViewModel` отвечает за вход, регистрацию, проверку существующей сессии и переход в гостевой режим. Она использует `LoginUseCase`, `RegisterUseCase` и `GetProfileUseCase`.

Состояние экрана передаётся через следующие LiveData:

- `loading` — выполняется ли запрос;
- `error` — текст ошибки или пустая строка при отсутствии ошибки;
- `openMain` — сигнал перехода на главный экран.

Операции авторизации выполняются через `ExecutorService`, а результаты фоновых операций публикуются с помощью `postValue`. `AuthActivity` наблюдает за состоянием и отображает сообщение, блокирует кнопки на время запроса или открывает главный экран.

### 3.2. Проверка данных и обработка ошибок авторизации

Дополнительно исправлена обработка ошибок, чтобы пользователь получал сообщение, соответствующее конкретной проблеме, а не устаревший общий текст.

Перед обращением к Firebase `AuthViewModel` проверяет:

1. Заполнен ли адрес электронной почты.
2. Соответствует ли адрес формату электронной почты.
3. Заполнен ли пароль.
4. Содержит ли пароль не менее шести символов.

Если проверка не пройдена, ошибка устанавливается сразу, сетевой запрос не запускается. При начале корректной попытки предыдущий текст ошибки очищается. В `AuthRepositoryImpl` перед выполнением входа и регистрации также очищается сохранённая ошибка последней операции.

`FirebaseAuthSource` преобразует известные ошибки Firebase в более понятные сообщения, в том числе:

| Ситуация | Сообщение |
|---|---|
| Пустая почта | `Введите адрес электронной почты.` |
| Некорректный формат почты | `Введите корректный адрес электронной почты.` |
| Пустой пароль | `Введите пароль.` |
| Пароль короче 6 символов | `Пароль должен содержать не менее 6 символов.` |
| Неверные учётные данные при входе | `Неверная почта или пароль.` |
| Почта уже зарегистрирована | `Аккаунт с такой почтой уже зарегистрирован.` |
| Ошибка подключения | `Нет подключения к сети. Проверьте интернет и повторите попытку.` |

Firebase может намеренно возвращать одинаковую ошибку для неизвестного пользователя и неправильного пароля при входе. В этом случае общее сообщение об ошибке учётных данных является ожидаемым поведением.

### 3.3. MainViewModel

`MainViewModel` отвечает за состояние главного экрана: получение профиля пользователя, загрузку каталога, поиск по штрихкоду, просмотр избранного, выход из аккаунта и демонстрационный вызов распознавания.

Основные LiveData:

- `currentUser` — текущий пользователь или гостевой профиль;
- `catalogFromNetwork` — каталог, полученный через мок-сетевой слой;
- `favoritesFromDb` — избранные продукты, загруженные из слоя хранения на основе Room;
- `catalogStorageSummary` — объединённая текстовая сводка двух источников;
- `message` — сообщения пользователю;
- `productFromBarcode` — найденный по штрихкоду продукт.

Загрузка данных выполняется в фоновом потоке. Activity подписывается на соответствующие LiveData и отображает результат, а не вызывает UseCase напрямую.

### 3.4. ProductDetailViewModel

`ProductDetailViewModel` отвечает за загрузку выбранного продукта и переключение его состояния в избранном. Информация о продукте, доступность операции добавления в избранное и сообщения публикуются через LiveData. `ProductDetailActivity` наблюдает за этими значениями и обновляет элементы существующего экрана.

### 3.5. FoodScanViewModelFactory

`FoodScanViewModelFactory` создаёт `AuthViewModel`, `MainViewModel` и `ProductDetailViewModel`. Зависимости берутся из текущего `ServiceLocator`. Каждая Activity получает нужную ViewModel через `ViewModelProvider`, поэтому фабрика централизует создание ViewModel и её зависимостей.

## 4. MediatorLiveData: объединение сетевого источника и Room

Контрольное задание требует получить данные из мок-сети и базы данных и объединить их с помощью `MediatorLiveData`.

В `MainViewModel` используются два источника:

| Источник | Переменная | Назначение |
|---|---|---|
| Мок-сетевой слой | `catalogFromNetwork` | Содержит продукты из каталога, загружаемого через `GetProductCatalogUseCase` и `NetworkApi` |
| Локальное хранилище Room | `favoritesFromDb` | Содержит сохранённые избранные продукты, получаемые через `GetFavoritesUseCase` |
| Объединённое состояние | `catalogStorageSummary` | Отображает количество продуктов в каталоге и количество избранных продуктов |

Источники добавляются в `MediatorLiveData` методом `addSource`:

```java
catalogStorageSummary.addSource(
        catalogFromNetwork,
        ignored -> updateCatalogStorageSummary()
);
catalogStorageSummary.addSource(
        favoritesFromDb,
        ignored -> updateCatalogStorageSummary()
);
```

Когда любой из источников обновляется, вызывается `updateCatalogStorageSummary()`. Метод формирует текстовую сводку. Если данные ещё загружаются, отображается состояние загрузки; после получения данных показывается количество элементов в каждом источнике.

Объединение выполняется на уровне состояния интерфейса: списки каталога и избранного остаются раздельными, а `MediatorLiveData` создаёт одну сводку об их текущем состоянии.

## 5. Проверка FoodScan

Проверка проводится после Gradle Sync и успешной сборки проекта в Android Studio.

### Авторизация

1. Открыть экран авторизации.
2. Нажать вход с пустой почтой — должно появиться сообщение о необходимости ввести почту.
3. Ввести некорректный адрес, например `test`, — должно появиться сообщение о некорректном формате почты.
4. Ввести корректную почту и пароль `12345` — должно появиться сообщение о минимальной длине пароля без запроса к Firebase.
5. Ввести корректный по формату адрес и пароль длиной от шести символов, но неверные учётные данные — должно появиться сообщение о неверной почте или пароле.
6. При доступной конфигурации Firebase проверить успешный вход и регистрацию, в том числе реакцию на уже зарегистрированную почту.
7. Проверить гостевой режим и открытие главного экрана.

### Каталог, избранное и MediatorLiveData

1. На главном экране дождаться загрузки каталога и сводки.
2. Убедиться, что сводка отдельно показывает состояние каталога из `NetworkApi` и избранного из Room.
3. Открыть карточку продукта и проверить отображение его сведений.
4. Авторизоваться, добавить продукт в избранное или удалить его.
5. Вернуться на главный экран и проверить, что количество избранных продуктов в сводке обновилось.
6. В гостевом режиме проверить ограничение доступа к операциям, требующим авторизации.
7. Проверить поиск по штрихкоду на существующем и отсутствующем в тестовом каталоге значениях.

## 7. Результаты и ограничения проверки

В рамках изменения кода логика работы с UseCase перенесена из Activity в ViewModel, состояние интерфейса публикуется через LiveData, а создание ViewModel осуществляется через ViewModelProvider и соответствующие фабрики. В `FoodScan` реализовано объединение сведений о сетевом каталоге и избранном с использованием MediatorLiveData. Также добавлена предварительная валидация полей авторизации и сопоставление известных ошибок Firebase понятным сообщениям.

Полная Gradle-сборка в рабочей среде не была подтверждена: Gradle Wrapper не смог загрузить дистрибутив Gradle 8.13 из-за отсутствия сетевого доступа. Поэтому фактический запуск и все пользовательские сценарии следует окончательно проверить в Android Studio. Скриншоты результатов необходимо добавить в отмеченные места после запуска приложений.

## Заключение

В результате практической работы изучен и применён архитектурный шаблон MVVM в двух Android-проектах. В `MovieProject` состояние любимого фильма передаётся от ViewModel к Activity через LiveData, а зависимости создаются через фабрику. В `FoodScan` логика авторизации, главного экрана и страницы продукта вынесена в отдельные ViewModel. Для контрольного задания `MediatorLiveData` наблюдает за мок-сетевым каталогом и данными избранного из Room и формирует общую сводку, автоматически обновляемую при изменении любого источника. Дополнительно улучшена обработка пользовательских ошибок при входе и регистрации. Структура существующих проектов и простой интерфейс сохранены.
