## 1. Цель работы

Цель практической работы — изучить принципы разделения мобильного приложения на слои, вынести операции локального хранения из репозитория в отдельный компонент, применять отдельные модели данных для разных уровней приложения и организовать работу с несколькими источниками данных.

В базовой части работа выполнялась на проекте `MovieProject`: логика сохранения любимого фильма была отделена от репозитория, а модели доменного слоя и локального хранилища разделены.

В контрольном задании дорабатывался проект `FoodScan`. Для него предусмотрены авторизация пользователей, сохранение данных о клиенте, работа с локальной базой избранных продуктов, получение каталога через тестовый JSON и отображение подробной информации о продукте.

## 2. Теоретические сведения

В приложении можно выделить несколько логических уровней:

- **Presentation / app** — экраны приложения, обработка действий пользователя и отображение результата.
- **Domain** — доменные модели, интерфейсы репозиториев и сценарии использования (Use Case). Этот слой описывает операции приложения и не должен зависеть от Android API или конкретных способов хранения.
- **Data** — реализация репозиториев, локальные хранилища, база данных и сетевой источник данных.
- **DTO и модели хранения** — структуры, предназначенные для получения данных из источника или записи в конкретное хранилище. Репозиторий преобразует их в доменные модели и обратно.

Такое разделение уменьшает связанность компонентов: замена механизма сохранения не требует менять пользовательский интерфейс или сценарии использования.

## 3. Базовая часть: MovieProject

### 3.1. Архитектура проекта

В исходной версии приложения репозиторий выполнял операции сохранения и получения фильма через `SharedPreferences`. В рамках практической работы логика хранения была выделена в отдельный компонент `MovieStorage`, а репозиторий стал посредником между доменной моделью и хранилищем.

Логическая структура решения:

```text
MovieProject/
├── app/       — MainActivity и ресурсы интерфейса
├── domain/    — доменная модель Movie, MovieRepository и Use Case
└── data/      — MovieRepositoryImpl и реализация MovieStorage
```

Основные классы слоя данных:

- `MovieStorage` — интерфейс чтения и сохранения;
- `SharedPrefMovieStorage` — реализация на основе `SharedPreferences`;
- `data.storage.models.Movie` — модель, используемая локальным хранилищем;
- `MovieRepositoryImpl` — преобразование моделей между слоями.

### 3.2. Интерфейс хранилища

Для отделения механизма хранения создан интерфейс `MovieStorage`. Он определяет две операции: получить ранее сохранённый фильм и сохранить новый объект.

```java
public interface MovieStorage {
    Movie get();
    boolean save(Movie movie);
}
```

Интерфейс позволяет заменить реализацию хранения, не изменяя контракт репозитория. Например, впоследствии реализацию на `SharedPreferences` можно заменить базой данных.

### 3.3. Реализация SharedPreferences

Класс `SharedPrefMovieStorage` отвечает за чтение и сохранение данных в локальном хранилище Android. В примере сохраняются идентификатор фильма, название и дата записи.

Ключевая часть метода сохранения:

```java
@Override
public boolean save(Movie movie) {
    if (movie == null || movie.getName() == null
            || movie.getName().trim().isEmpty()) {
        return false;
    }

    return preferences.edit()
            .putString(KEY_NAME, movie.getName().trim())
            .putString(KEY_DATE, LocalDate.now().toString())
            .putInt(KEY_ID, movie.getId())
            .commit();
}
```

При получении значения проверяется, выполнялось ли ранее сохранение. Если данных нет, метод возвращает `null`, а не создаёт фиктивную запись.

```java
@Override
public Movie get() {
    if (!preferences.contains(KEY_NAME)) return null;

    String name = preferences.getString(KEY_NAME, "");
    String date = preferences.getString(KEY_DATE, "");
    int id = preferences.getInt(KEY_ID, -1);
    return new Movie(id, name, date);
}
```

### 3.4. Преобразование моделей в репозитории

Доменная модель `Movie` содержит данные, необходимые бизнес-логике приложения. Модель хранилища дополнительно содержит дату локального сохранения. Репозиторий преобразует одну модель в другую, чтобы остальные слои не зависели от формата `SharedPreferences`.

```java
@Override
public boolean saveMovie(Movie movie) {
    if (movie == null || movie.getName() == null
            || movie.getName().trim().isEmpty()) {
        return false;
    }
    return movieStorage.save(mapToStorage(movie));
}

@Override
public Movie getMovie() {
    ru.mirea.khrechko.movieproject.data.storage.models.Movie stored =
            movieStorage.get();
    return stored == null ? null : mapToDomain(stored);
}
```

В примере используется полное имя модели из пакета `data.storage.models`, поскольку доменная модель и модель хранения имеют одинаковое имя класса.

Зависимости создаются в точке сборки приложения: сначала создаётся `SharedPrefMovieStorage`, затем он передаётся в конструктор `MovieRepositoryImpl`.

```java
MovieStorage storage = new SharedPrefMovieStorage(getApplicationContext());
MovieRepository repository = new MovieRepositoryImpl(storage);
```

### 4.2. Логические слои и основные классы

В коде приложения выделены компоненты, отвечающие за интерфейс, доменные сценарии и источники данных.

| Уровень | Основные классы / назначение |
|---|---|
| Presentation (`app`) | `AuthActivity`, `MainActivity`, `ProductAdapter`, `ProductDetailActivity` |
| Domain | `Product`, `User`, интерфейсы репозиториев, `LoginUseCase`, `FindProductByBarcodeUseCase`, сценарии избранного |
| Data | `FirebaseAuthSource`, `SharedPrefUserStorage`, `FoodScanDatabase`, `FavoriteProductDao`, `NetworkApi`, реализации репозиториев |
| DI | `ServiceLocator` создаёт источники данных и репозитории и предоставляет их Activity |

`MainActivity` получает зависимости через `ServiceLocator`, показывает каталог и обрабатывает переходы на экран продукта. `ProductAdapter` подготавливает карточки для списка, а `ProductDetailActivity` отображает сведения о выбранном товаре.

**Примечание о Gradle-модулях.** Если файлы `data` и `domain` в рабочем проекте находятся в `app/src/main/java/ru/mirea/khrechko/foodscan/`, это логические пакеты, а не отдельные Gradle-модули. По буквальному требованию контрольного задания следует вынести их в модули `data` и `domain`, после чего подключить в `settings.gradle.kts`. Перенос одних Java-файлов в подпапки не создаёт Gradle-модулей.

### 4.3. Авторизация через Firebase Authentication

Для входа и регистрации используется Firebase Authentication с электронным адресом и паролем. `AuthActivity` собирает данные из полей ввода, передаёт их в Use Case и показывает результат. Сетевые операции выполняются в отдельном потоке, чтобы не блокировать пользовательский интерфейс.

В слое `data` класс `FirebaseAuthSource` обращается к Firebase SDK. Основной вызов входа выглядит следующим образом:

```java
FirebaseUser user = Tasks.await(
        firebaseAuth.signInWithEmailAndPassword(email, password)
).getUser();
```

Полученный объект Firebase преобразуется в DTO пользователя, а затем репозиторий возвращает доменную модель `User`. При регистрации также задаётся отображаемое имя пользователя. При выходе вызывается `signOut()` и очищаются локальные данные профиля.

Для подключения Firebase необходимы:

1. Firebase-проект с Android-приложением `ru.mirea.khrechko.foodscan`.
2. Включённый способ входа Email/Password.
3. Файл `google-services.json` в каталоге `app`.
4. Google Services Gradle Plugin и зависимость Firebase Authentication.

Файл `google-services.json` является индивидуальным для Firebase-проекта и не включается в исходный код отчёта.

### 4.4. SharedPreferences для хранения данных клиента

Для локального хранения информации о пользователе применяется `SharedPrefUserStorage`. В нём сохраняются UID, электронная почта, отображаемое имя и время последнего входа. Пароль в локальном хранилище не сохраняется.

Ключевая часть метода `save`:

```java
return preferences.edit()
        .putString(KEY_UID, user.getUid())
        .putString(KEY_EMAIL, user.getEmail())
        .putString(KEY_NAME, user.getDisplayName())
        .putLong(KEY_LAST_LOGIN, user.getLastLoginMillis())
        .commit();
```

Для выхода из профиля вызывается очистка локального хранилища. При этом сессией Firebase управляет сам Firebase Authentication.

### 4.5. Room для локального хранения избранного

Для избранных продуктов используется Room — библиотека над SQLite. `FoodScanDatabase` описывает базу данных, `FavoriteProductEntity` — структуру записи, а `FavoriteProductDao` — операции чтения, добавления и удаления.

В записи избранного хранятся идентификатор пользователя, идентификатор продукта и данные, необходимые для отображения карточки. Составной первичный ключ не позволяет одному пользователю добавить один и тот же продукт повторно.

```java
import androidx.annotation.NonNull;
import androidx.room.Entity;

@Entity(
    tableName = "favorite_products",
    primaryKeys = {"userId", "productId"}
)
public class FavoriteProductEntity {
    @NonNull
    public String userId;
    public int productId;
    public String name;
    public String brand;
    public String imageUrl;
    public String ingredients;
    public int calories;
}
```

Для поля строкового первичного ключа `userId` используется `@NonNull`, чтобы Room мог корректно сформировать таблицу. В DAO предусмотрены запросы с фильтрацией по UID текущего пользователя:

```java
@Query("SELECT * FROM favorite_products WHERE userId = :userId ORDER BY name")
List<FavoriteProductEntity> getByUserId(String userId);
```

`FavoriteRepositoryImpl` переводит записи Room в доменные объекты `Product` и обратно. Операции с базой выполняются вне главного UI-потока.

### 4.6. NetworkApi и тестовые JSON-данные

Для демонстрации работы с внешним источником данных создан `NetworkApi`. В текущем варианте он использует встроенную JSON-строку с пятью примерами продуктов, разбирает её через `JSONArray` и создаёт объекты `ProductDto`.

Пример объекта из тестового JSON:

```json
{
  "id": 2,
  "barcode": "460000000002",
  "name": "Банан",
  "brand": "FoodScan",
  "ingredients": "Банан",
  "calories": 89
}
```

Каталог содержит пять демонстрационных штрихкодов: `460000000001`–`460000000005`. Репозиторий перебирает полученные DTO, ищет совпадение по штрихкоду и преобразует найденную запись в доменную модель `Product`.

```java
@Override
public Product findByBarcode(String barcode) {
    if (barcode == null) return null;
    String target = barcode.trim();

    for (ProductDto dto : networkApi.getProducts()) {
        if (dto.barcode.equals(target)) {
            return mapToDomain(dto);
        }
    }
    return null;
}
```

Таким образом, текущий `NetworkApi` является мокированным источником данных и не делает настоящий HTTP-запрос к Open Food Facts. В будущем его реализацию можно заменить сетевым клиентом, сохранив интерфейс доменного репозитория.

### 4.7. Поиск по штрихкоду и карточка продукта

На главном экране пользователь может открыть диалог поиска, ввести штрихкод и подтвердить действие. `FindProductByBarcodeUseCase` обращается к репозиторию. Если продукт найден, приложение открывает `ProductDetailActivity` и передаёт ей идентификатор, название, бренд, изображение, состав и калорийность через `Intent`.

Пример передачи данных на экран товара:

```java
Intent intent = new Intent(this, ProductDetailActivity.class);
intent.putExtra("product_id", product.getId());
intent.putExtra("product_name", product.getName());
intent.putExtra("product_brand", product.getBrand());
intent.putExtra("product_image", product.getImageUrl());
startActivity(intent);
```

`ProductDetailActivity` отображает подробную информацию о товаре, а Glide используется для загрузки изображения по URL. Activity должна быть объявлена в `AndroidManifest.xml`:

```xml
<activity
    android:name=".ProductDetailActivity"
    android:exported="false" />
```

При проверке была устранена ошибка `ActivityNotFoundException`: после объявления `ProductDetailActivity` в манифесте переход от поиска штрихкода к карточке продукта стал доступен.

### 4.8. Проверка FoodScan

В процессе отладки были устранены ошибки, связанные с конфигурацией Firebase, генерацией реализации Room и объявлением `ProductDetailActivity` в манифесте. После исправления объявления Activity приложение смогло переходить от поиска по штрихкоду к карточке товара.

Перед окончательной сдачей рекомендуется пройти проверки из таблицы и отметить фактический результат в последнем столбце.

| Проверка | Ожидаемый результат | Фактический результат |
|---|---|---|
| Запуск приложения | Открывается экран авторизации или главный экран в зависимости от состояния пользователя | Заполнить после итогового запуска |
| Авторизация / регистрация | Firebase принимает корректные данные и возвращает пользователя в приложение | Заполнить после проверки с реальным аккаунтом Firebase |
| Вход как гость | Каталог доступен без входа; избранное ограничено | Заполнить после проверки |
| Поиск по тестовому штрихкоду `460000000002` | Открывается карточка продукта «Банан» | Переход от поиска к карточке проверен после добавления Activity в манифест |
| Несуществующий штрихкод | Показывается сообщение, что продукт не найден | Заполнить после проверки |
| Добавление в избранное | Продукт сохраняется для вошедшего пользователя | Заполнить после проверки Room |
| Перезапуск приложения | Ранее сохранённый избранный продукт доступен после перезапуска | Заполнить после проверки Room |

В базовой части `MovieProject` рассмотрено разделение механизма локального хранения и репозитория: появился интерфейс `MovieStorage`, отдельная реализация `SharedPrefMovieStorage`, модель данных для хранения и преобразование между моделью хранения и доменной моделью. Такой подход снижает связанность кода и упрощает будущую замену источника данных.

В контрольном задании `FoodScan` подготовлены интерфейсные экраны, сценарий поиска продуктов по штрихкоду, подробная карточка продукта, Firebase Authentication, сохранение данных клиента в `SharedPreferences`, локальное хранилище избранного на Room и мокированный `NetworkApi`, формирующий каталог из JSON. Также подготовлен анализ возможных моделей TensorFlow Lite.

В ходе запуска были исправлены ошибки настройки Firebase, генерации классов Room и объявления `ProductDetailActivity` в `AndroidManifest.xml`. Поиск по тестовому штрихкоду после исправления перехода открывает карточку продукта.
